Components for assistants

A working document for the team building the component library that assistants in the shared solution (fellesløsningen) are made from. It collects what each component does, its variants, and what we learn as we build and test.

Last updated 19 October 2026 · Grows as we build · Not meant for service owners yet.

Overview

The components are grouped by where they sit: the conversation in the main area, the primary sidebar with threads, and the tools in the secondary sidebar.

Conversation · main area

  • Chat Question in, answer out, in one thread. DraftAlways included?
  • Approach The steps the assistant takes to answer. DraftOptional
  • Footnotes Numbers in the answer that point to the source. DraftOptional

Threads and filter · primary sidebar

  • Threads The conversations, and a new thread. DraftOptional
  • Filter Choose which documents a thread reads from. DraftOptional
  • Projects Groups threads, documents and instructions. DraftOptional

Tools · secondary sidebar

  • Sources The documents and excerpts behind the answer. DraftOptional
  • Document view The whole document, with the excerpt marked. DraftOptional
  • Notes Collect excerpts, and keep the sources. DraftOptional

About these pages

How the pages work

Select a component above to open its page. Every component page has the same parts, in the same order:

  1. What it does, and where it sits in the interface
  2. Use it when, and don't use it when
  3. Variants
  4. Related components
  5. What we have learned
  6. Open questions

Norwegian words in «quotes» are the text users see in the interface.

Phases

Each component is in one of four phases:

  • Draft: explored in the design canvas, not built yet.
  • Building: work in progress in the code.
  • Testing: built, and being tested with users.
  • Ready: can be chosen when an assistant is set up.

All components are drafts for now. The list of components follows #167. What we have learned comes from the canvas Fellesløsningen.

Putting an assistant together

Whoever sets up the assistant chooses which components it has. These rules hold for every combination.

Rules

  1. A component that is not included is not shown. No empty panels, tabs or buttons that point to something that isn't there.
  2. Without a filter, a thread reads from a fixed set of documents chosen when the assistant is set up. There is no filter panel and no «Endre».
  3. The tools panel follows the number of tools: one gives just a heading, two give a tab selector, three or more give a dropdown. See #168.

Which component meets which need

  • “a way to choose documents” → Filter
  • “to see where the answer comes from” → Footnotes and Sources
  • “to see what the assistant did” → Approach
  • “to read the whole document” → Document view
  • “to collect and reuse answers” → Notes
  • “to work on a case over time” → Projects
  • “to come back to earlier conversations” → Threads

Shared across components

What we have learned that applies to more than one component.

Visual language

  • Floating white panels, round corners and plenty of space. Avoid sharp white/grey/white stripes.
  • Colours are chosen by their role in Designsystemet, not by how they look.
  • Tab selector: a grey rail with a white selected tab, not black and white.
  • Designsystemet first. Flag deviations, and use the theme's levers before custom styling.
  • Use everyday words (klarspråk).

Keeping the pages up to date

When a component changes

  • Update its page in the same PR that changes the component: phase, variants and what we learned.
  • Update its badges in the overview here, and add a line to the change log.
  • What is still a hypothesis is marked as one.

When a component is added

  • Only components listed in #167. The canvas is a source of learnings, not the list.
  • A sketch in the overview, a page of its own with the same parts, and a line in the change log.
  • Issue for these pages: #171.
